# MedicalAI 端到端业务闭环优化计划

## 总体目标

在“内部试运行”范围内完成一条可靠闭环：

患者手动维护 → 创建接诊 → 浏览器录音或上传完整音频 → 异步转写 → 医生核对转写 → AI 生成病历 → 医生编辑并确认 → 后端生成 DOCX/PDF → 权限控制下载 → 结束接诊。

本阶段采用真实 AI 服务、MinIO 对象存储和后端文件导出；暂不实现 WebSocket 实时转写，浏览器录音停止后以完整 WebM 文件上传。

---

## 第 0 步：先修复基础运行环境和现有数据问题

### 目标

保证后端、AI 服务、PostgreSQL、MinIO、前端通过 Docker Compose 能够稳定启动，避免后续功能建立在错误配置上。

### 调整内容

- 统一 API 端口配置：
  - Spring Boot 和 Compose 统一使用 `8080`，或统一使用 `8189`，只能保留一个端口。
- 修正数据库连接：
  - API 使用 Compose 内的 `postgres` 服务名；
  - 用户名、密码、数据库名与 PostgreSQL 容器一致。
- 补充 MinIO 配置：
  - endpoint、access key、secret key、bucket；
  - 录音和导出文件分别使用明确的对象前缀。
- 启动时检查：
  - 数据库连接；
  - Flyway 迁移；
  - MinIO bucket 是否存在；
  - AI 服务健康状态。
- 增加统一错误响应和 request id，便于排查跨服务问题。

### 验收标准

- `docker compose up` 后所有核心服务健康；
- Flyway 可重复启动；
- API 能访问数据库和 MinIO；
- 前端能正常调用 API；
- 录音和导出文件不会写入容器临时目录。

## 第 1 步：完善患者手动管理

患者不再只依赖 Demo Provider，改为后端数据库 CRUD，保留手动录入方式。

### 新增接口

```text
POST   /api/v1/patients
GET    /api/v1/patients
GET    /api/v1/patients/{patientId}
PUT    /api/v1/patients/{patientId}
POST   /api/v1/patients/{patientId}/disable
```

### 患者字段

至少支持：

```text
patient_no
name
gender
birth_date
phone
id_no
department_id
department_name
status
```

数据库中：

- 电话只返回脱敏值；
- 身份证保存 hash 或加密值，接口只返回脱敏值；
- `source_system=''LOCAL''` 表示手动录入；
- 患者编号或“姓名 + 手机后四位”重复时返回 409；
- 停用患者不能创建新接诊，但历史接诊仍可查看。

### 业务规则

- 创建患者和创建接诊分离；
- 创建接诊时保存患者快照；
- 修改患者不会修改历史接诊数据；
- 患者停用需要写审计日志；
- 患者列表支持关键字、状态和分页；
- 所有患者接口只允许当前医生访问本院数据。

### 验收标准

- 可以手动新增、查询、编辑、停用患者；
- 停用患者无法创建接诊；
- 历史接诊仍能正常查看；
- 敏感字段不会在响应中返回明文；
- 重复患者能得到明确的 409 错误。

## 第 2 步：统一录音上传流程

一期采用“整段录音上传后转写”，同时支持两种来源：

1. 浏览器 `MediaRecorder` 录音，停止后生成 WebM 文件并上传；
2. 用户选择本地完整音频文件后上传。

两种方式在后端统一为 `recording` 数据模型。

### 接口调整

保留现有接口：

```text
POST /api/v1/visits/{visitId}/recordings
GET  /api/v1/visits/{visitId}/recordings
GET  /api/v1/recordings/{recordingId}/audio
```

新增或补充：

```text
POST /api/v1/visits/{visitId}/recordings/{recordingId}/transcribe
GET  /api/v1/recordings/{recordingId}/transcribe-jobs/{jobId}
POST /api/v1/recordings/{recordingId}/cancel
```

`POST /recordings` 使用 multipart：

```text
file
source_type: BROWSER | UPLOAD
duration_ms
mime_type
client_request_id
```

### 录音状态

```text
UPLOADED
QUEUED
PROCESSING
DONE
FAILED
CANCELLED
```

### 存储

- 录音写入 MinIO；
- 数据库只保存 object key、大小、MIME、时长、hash；
- 上传成功后再写数据库记录；
- 如果数据库写入失败，清理孤儿对象；
- 通过后端鉴权接口读取音频，禁止直接暴露公开 bucket；
- 对上传文件做扩展名、MIME、文件头和大小校验；
- 计算 SHA-256，支持重复上传检测。

### 浏览器录音行为

前端：

1. 检查 `MediaRecorder` 支持；
2. 请求麦克风权限；
3. 录音中显示计时和停止按钮；
4. 停止后生成 WebM Blob；
5. 上传完成后展示录音状态；
6. 用户点击“开始转写”。

一期不实现实时音频 WebSocket，不要求边录边转。

### 验收标准

- 浏览器录音可上传并回放；
- MP3、WAV、M4A、WEBM 可上传；
- 超大文件、空文件、伪造 MIME 能被拒绝；
- 同一文件重复上传有明确结果；
- 录音文件可在服务重启后继续读取；
- 上传失败不会留下不可追踪的数据。

## 第 3 步：引入统一异步任务框架

现有 `ai_job` 表要真正参与 ASR 和病历生成，避免同步请求阻塞和重复生成。

### 任务类型

```text
ASR_TRANSCRIBE
MEDICAL_RECORD_GENERATE
EXPORT_DOCX
EXPORT_PDF
```

### 任务状态

```text
PENDING
RUNNING
SUCCEEDED
FAILED
CANCELLED
```

### 通用任务字段

增加或确认：

```text
job_id
job_type
visit_id
recording_id
record_id
source_snapshot_hash
idempotency_key
attempt_count
last_error
started_at
finished_at
```

### 接口行为

转写：

```text
POST /api/v1/visits/{visitId}/recordings/{recordingId}/transcribe
→ 202 { job_id, status: "PENDING" }

GET /api/v1/asr-jobs/{jobId}
→ 当前状态、进度、错误信息、结果引用
```

病历生成：

```text
POST /api/v1/visits/{visitId}/medical-record/generate
→ 202 { job_id, status: "PENDING" }

GET /api/v1/medical-record-jobs/{jobId}
```

### 任务规则

- `client_request_id + 业务对象 + 任务类型` 形成幂等键；
- 同一快照只允许一个有效生成任务；
- 失败自动重试，最多 3 次；
- AI 超时、网络错误、格式错误分别记录；
- 任务完成后更新业务表；
- 任务执行器启动时恢复超时的 `RUNNING` 任务；
- 前端使用轮询，初期不引入消息推送。

### AI 接入

后端增加 AI Provider 接口：

```text
transcribe(objectKey, metadata)
generateMedicalRecord(snapshotHash, dialogue, patient)
```

实现：

- `RealAiProvider`：真实 ASR/病历服务；
- `MockAiProvider`：测试和本地演示；
- 通过配置切换；
- 保存 provider、模型版本和响应摘要；
- 严格校验 AI 返回的 snapshot hash、状态和字段。

### 验收标准

- 长音频不会阻塞 HTTP 请求；
- 重复点击不会创建重复任务；
- AI 服务暂时不可用时任务进入 FAILED 并返回可读错误；
- 服务重启后任务可以恢复；
- 前端可以看到排队、处理中、完成和失败状态。

## 第 4 步：完善转写结果和对话快照

### 数据流

```text
录音对象
→ ASR 任务
→ utterances
→ 医生核对/编辑
→ dialogue_snapshot
→ 病历生成
```

### 接口

保留：

```text
GET /api/v1/visits/{visitId}/transcript
PUT /api/v1/visits/{visitId}/transcript
```

增加：

```text
POST /api/v1/visits/{visitId}/transcript/adopt
GET  /api/v1/visits/{visitId}/transcript/versions
```

### 规则

- ASR 原始结果不可覆盖；
- 医生编辑生成新的 transcript 版本；
- 只有 `ADOPTED` snapshot 才能用于病历生成；
- 录音或转写发生变化后，旧病历标记 `source_dirty=true`；
- 病历确认前必须使用最新 adopted snapshot；
- utterance 保存角色、时间戳、文本、来源录音和修订号。

### 验收标准

- 可以查看原始转写和当前采用版本；
- 医生编辑后可以保存并重新生成；
- 病历能识别转写变化；
- 已确认病历不能直接覆盖其来源快照。

---

## 第 5 步：完善病历生成、编辑和确认状态机

### 状态流转

```text
NO_RECORD
→ GENERATING
→ DRAFT
→ EDITING
→ CONFIRMED
→ EDITING_NEW_VERSION
→ DRAFT
```

### 接口

```text
GET  /api/v1/visits/{visitId}/medical-record
POST /api/v1/visits/{visitId}/medical-record/generate
PUT  /api/v1/visits/{visitId}/medical-record
POST /api/v1/visits/{visitId}/medical-record/edit
POST /api/v1/visits/{visitId}/medical-record/confirm
GET  /api/v1/visits/{visitId}/confirmations
```

### 规则

- 每次 AI 生成创建新版本；
- 每次确认绑定明确版本；
- 确认后不能直接修改原版本；
- “修改病历”创建新版本；
- 重新生成会明确提示覆盖当前草稿；
- 确认时检查：
  - 患者身份字段；
  - 主诉；
  - 现病史；
  - 医生；
  - 当前来源快照未变化；
  - 当前版本不是已确认版本。
- 保存 AI 原始内容和医生编辑后的内容；
- 保存生成模型、生成时间和操作者。

### 结束接诊条件

接诊只有在以下条件同时满足时才能完成：

```text
录音任务不存在 PROCESSING
所有采用录音已完成转写
当前病历已确认
当前版本没有 source_dirty
所有导出任务已完成或明确允许跳过
```

## 第 6 步：实现后端 DOCX/PDF 生成和下载

导出不再只记录 `client-generated`，改为后端真实生成文件。

### 接口

```text
POST /api/v1/visits/{visitId}/exports
GET  /api/v1/visits/{visitId}/exports
GET  /api/v1/exports/{exportId}
GET  /api/v1/exports/{exportId}/download
```

### 导出规则

- 只允许导出当前已确认版本；
- 导出记录绑定：
  - record_id；
  - version_id；
  - confirmation_id；
  - format；
  - object_key；
  - file size；
  - file hash；
  - created_by。
- 导出任务异步执行；
- 成功后返回受鉴权保护的下载接口；
- 文件名包含患者名、接诊编号和版本号；
- 下载动作写入审计日志；
- 不提供公开 URL；
- 文件生成失败时状态为 `FAILED`，可重新发起。

### 格式实现

- DOCX：后端使用稳定的 DOCX 库生成；
- PDF：后端按固定 A4 模板生成；
- 模板字段与前端病历字段一致；
- 导出内容必须包含：
  - 患者信息；
  - 接诊编号；
  - 病历版本；
  - 病历正文；
  - 确认医生；
  - 确认时间；
  - 导出时间。

### 验收标准

- DOCX 可以被 Word 正常打开；
- PDF 页面布局稳定；
- 未确认病历无法导出；
- 非当前医生无法下载；
- 导出文件在服务重启后仍可下载；
- 导出状态与实际文件存在性一致。

## 第 7 步：权限、审计和安全补齐

### 权限

最少区分：

```text
DOCTOR
ADMIN
```

医生只能访问自己的接诊；管理员可按配置查看院内数据。

### 审计事件

统一记录：

```text
PATIENT_CREATED
PATIENT_UPDATED
PATIENT_DISABLED
VISIT_CREATED
VISIT_STARTED
RECORDING_UPLOADED
TRANSCRIBE_STARTED
TRANSCRIPT_EDITED
RECORD_GENERATED
RECORD_EDIT_STARTED
RECORD_CONFIRMED
EXPORT_CREATED
EXPORT_DOWNLOADED
VISIT_COMPLETED
```

### 安全要求

- 演示登录只能保留为显式开发模式；
- 内部试运行至少使用真实登录 token 或受控账号；
- 所有下载接口重新校验权限；
- 日志禁止打印音频内容、身份证明文和访问 token；
- 限制上传频率和单文件大小；
- 所有外部 AI 请求设置连接和读取超时；
- 对 MinIO object key 做路径隔离；
- 代理环境下正确处理客户端 IP。

## 第 8 步：测试和验收

### 单元测试

覆盖：

- 患者 CRUD 和重复校验；
- 接诊状态流转；
- 录音状态流转；
- 任务幂等；
- 任务重试；
- 快照版本；
- 病历版本；
- 确认约束；
- 导出权限；
- 文件路径和对象 key 校验。

### 集成测试

使用 PostgreSQL 和 MinIO 测试容器验证：

- Flyway 全量迁移；
- 患者创建到接诊创建；
- 录音上传到对象存储；
- ASR 任务完成后生成快照；
- 病历生成和确认；
- DOCX/PDF 导出和下载；
- 服务重启后的任务恢复。

### 端到端测试

至少覆盖以下场景：

1. 新增患者 → 新建接诊 → 浏览器录音 → 上传 → 转写 → 生成病历 → 确认 → DOCX 下载 → 完成接诊。
2. 新增患者 → 上传完整 MP3 → 转写 → 编辑转写 → 重新生成病历。
3. AI 服务不可用 → 任务失败 → 重试成功。
4. 医生确认后追加录音 → 病历变为脏数据 → 新建版本 → 重新确认。
5. 未确认病历尝试导出 → 返回 409。
6. 非接诊医生访问录音、病历或导出 → 返回 404/403。
7. 浏览器录音上传中断 → 任务和文件状态可恢复或明确失败。
8. 重复点击上传、转写、生成和导出 → 不产生重复业务结果。

### 验收指标

- 核心接口成功率不低于 99%；
- 录音上传失败不会产生孤儿数据库记录；
- AI 任务可重试、可恢复；
- 病历确认和导出版本永远一致；
- 每个业务步骤都有可追踪审计记录；
- 前端不需要自行伪造 DOCX/PDF；
- API、前端和 Docker Compose 配置一致。

---

## 实施顺序

建议按以下顺序逐步交付：

1. Compose、端口、数据库、MinIO 和健康检查；
2. 患者 CRUD；
3. MinIO 录音上传和浏览器整段录音；
4. ASR 异步任务；
5. 转写快照和医生编辑；
6. 病历生成异步化；
7. 病历确认和接诊完成约束；
8. 后端 DOCX/PDF 导出；
9. 权限、审计和安全；
10. 集成测试和端到端验收。

每一步完成后都应保持前一步流程可用，避免一次性替换整个链路。

---

## 默认假设

- 本阶段是单院内部试运行，不做多租户；
- 患者由系统手动维护，不接外部 HIS 患者同步；
- 浏览器录音采用 `MediaRecorder`，停止后上传完整文件；
- 一期不做实时 WebSocket 转写；
- ASR 和病历生成通过可替换 Provider 接入真实 AI；
- MinIO 同时保存录音和导出文件；
- 后端负责生成和下载 DOCX/PDF；
- 保留 Mock Provider 仅用于自动化测试和本地开发；
- 现有前端流程和接口命名尽量兼容，新增接口通过版本化方式逐步替换旧的同步接口。
